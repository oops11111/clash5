## 一、请你先完成的实现（M0）

### M0.1 基建 `[标准]`
若尚无 git 远程 fork：在回复里列出需要用户提供的 GitHub fork URL，并先在本仓库内完成可本地验证的骨架：
- `README.md` 写明产品名 **clash5**、GPL-3.0、上游为 clash-verge-rev `dev`、同步方式 merge（S2）
- 增加最小 CI 描述或 workflow 草稿（lint/typecheck/cargo test + 配置快照为目标，T2）
- 保持 `sources/` 只读，不改其中已同步文件

### M0.2 数据骨架 `[Opus]`
在 `src/`（语言可先用 Rust 模块或 TypeScript，二选一写清理由；若尚未接 Verge 仓库，先做**可单测的独立库**亦可）实现：

1. **StableId**
   `hash(type + server + port + 归一化凭证)`；不依赖显示名。

2. **BindingStore（SQLite）**
   表至少含：bindings、chains、quality_cache（可空实现）、audit_log、orphan 标记；来源字段区分 `manual` / `subscription`（C2）。

3. **订阅 diff**
   - 匹配 → 继承绑定
   - 新增 → 无绑定
   - 消失 → **orphan（A2）**；`stable_id` 恢复后自动重绑
   - 名称模糊匹配：**默认关闭（B）**

4. **单测**（必须绿）
   - 同节点改名后 stable_id 不变
   - 消失→orphan→恢复后绑定还在
   - 手动节点不被「订阅刷新」删掉

非目标：UI 精修、sing-box、注入、插件 Host、真连机场。

## 二、功能验收清单（全部勾选才算 M0 通过）

在实现完成后，**逐项执行并贴出证据**（命令输出或简短日志）。任何一项失败 = M0 未通过。

### A. 仓库与文档
- [ ] A1 README 含 clash5、GPL、上游与 merge 策略
- [ ] A2 `docs/` 中可找到工程手册与本验收文档
- [ ] A3 未把订阅 URL / 节点凭证写入仓库

### B. StableId
- [ ] B1 两节点仅显示名不同、指纹字段相同 → stable_id 相同
- [ ] B2 改 port 或 uuid/password → stable_id 不同
- [ ] B3 单元测试覆盖 B1/B2

### C. 绑定与来源隔离（C2）
- [ ] C1 可为 manual 节点写入 binding
- [ ] C2 可为 subscription 节点写入 binding
- [ ] C3 列表/查询能区分来源；清理策略可按来源过滤（至少代码路径存在）

### D. Orphan（A2）
- [ ] D1 fixture：订阅刷新去掉某 stable_id → binding 标记 orphan，不硬删（或等价可恢复存储）
- [ ] D2 同 stable_id 再次出现 → binding 自动关联且 enabled 状态符合设计
- [ ] D3 提供清理全部 orphan 的 API 或 CLI/函数
- [ ] D4 名称匹配关闭时：仅改名、指纹变 → **不会**误重绑（B）

### E. 测试命令
- [ ] E1 文档写明一键测试命令（例如 `cargo test` 或 `pnpm test` / `python -m pytest`）
- [ ] E2 上述命令在本机项目目录执行退出码 0
- [ ] E3 无网络依赖；失败信息可读

### F. 明确未做（须在报告中声明）
- [ ] F1 声明 M1+ 未做
- [ ] F2 声明未接真实 Mihomo 热加载（若未接）
