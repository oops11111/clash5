# M1 desktop demo script

Run this against a built clash5 desktop shell with Mihomo available. Use disposable proxy credentials and keep links out of screenshots and logs. Record the app version, platform, results and any deviation in the M1 issue before accepting the milestone.

1. Start the shell with `pnpm dev`. Open **Nodes** and confirm the inventory comes from the active profile. The empty state must not show sample nodes or fabricated latency.
2. Copy a valid standalone proxy URI to the clipboard and use **Import from clipboard**. Confirm one manual row appears. Restart the shell and confirm the same row persists. Import the same URI with a different display name; it must update that row rather than create a second identity.
3. For a disposable local fixture, start `pnpm m1:probe-fixture 18080 forward` and `pnpm m1:probe-fixture 18081 limit` in separate terminals. On Windows, confirm that both `curl.exe -x http://127.0.0.1:18080 http://cp.cloudflare.com/generate_204` and `curl.exe -k -x http://127.0.0.1:18080 https://cp.cloudflare.com/generate_204` return 204 before using the forwarding endpoint. Import `http://127.0.0.1:18080/#M1-forward` and `http://127.0.0.1:18081/#M1-limit`; the latter replies 429 to HTTP and CONNECT requests. Run **Probe**. The forwarding node should receive a measured result and the limited node should fail; one failure must not hide the other result or abort the batch. Run **Probe** again immediately and confirm both results are reported as cached. Compare each fixture's `http://127.0.0.1:<port>/__stats` counters before and after the cached run; they must not increase.
4. Import the fixture subscription `http://127.0.0.1:18080/subscription.yaml`, which includes `M1-inline` and an external `M1-remote` provider. Confirm the two source scopes are distinct in the node table. Add a local rule and customize the `M1-selected` group in the profile editor. Switch the fixture with `curl.exe -X POST http://127.0.0.1:18080/__phase/2`, then refresh the subscription in the app. Confirm the changed inline endpoint appears, its old identity becomes inactive, and the local rule and group remain. A repeated identity must show a duplicate count without merging records from different sources.
5. Select the manual, inline and external-provider rows and run **Probe**. Confirm each maps to its intended runtime proxy. An unavailable or ambiguous runtime name must be counted as unavailable, without probing another node. Sort by quality and filter by source, duplicates, high quality and inactive state; compare the layout with `src/ui-hifi/src/pages/Nodes.tsx`.

The automated data test covers persisted cache compatibility and 10/20/40/60-minute retry intervals. The command test covers failure isolation within a probe batch. `pnpm m1:mihomo-smoke <mihomo-binary>` verifies actual HTTP and HTTPS delay requests through Mihomo against the forwarding and 429 fixture proxies. This desktop script is still required because those tests do not prove the Tauri-to-Mihomo command path or UI behavior. The 429 fixture verifies that a limited proxy fails; the command records that as a generic failure and applies its retry backoff. The current Mihomo delay API does not expose the upstream HTTP status to this command, so the app cannot label that failure specifically as a provider 429 or honor its `Retry-After` value.

The manually dispatched Windows workflow runs `pnpm m1:desktop-smoke <app-binary> --full` against a fresh desktop session. That check imports disposable localhost links through the page's clipboard button, confirms renaming does not create a duplicate identity, probes both fixture proxies through the running app, and verifies an immediate retry uses cached results without new fixture traffic. It does not cover subscription refresh, user rule preservation, or the complete visual walkthrough above; record those separately before accepting M1.
